# 0027. Better Auth integration

- Status: Accepted
- Date: 2026-11-23
- Amends: [0026](0026-public-pages-and-landing-route.md)

## Context
[ADR 0004](0004-auth-with-better-auth-and-google.md) chose Better Auth with Google, [ADR 0005](0005-per-user-data-isolation.md) requires the user id to come only from the server-side session, and [ADR 0025](0025-database-schema-implementation.md) prepared the tables. This record fixes how the pieces are wired.

## Decision
- **Mounting.** Better Auth's handler is mounted at `/api/auth/*` inside the Hono app. The web app talks to it through the Better Auth client on the same origin, so session cookies are first-party and no CORS is configured.
- **Schema mapping.** The Drizzle adapter receives the existing `user`, `session`, `verification` tables and `auth_account`, with `account.modelName` set to `auth_account`. `advanced.database.generateId` is `"uuid"`, as ADR 0025 requires. `user.locale` is declared as an additional field (not accepted from clients, default `es`).
- **Provider and cookies.** Google is the only provider. Cookies are `httpOnly`, `sameSite=lax`, and `secure` whenever `BETTER_AUTH_URL` is https.
- **First sign-in.** A `user.create.after` database hook calls `seedUserDefaults`. If seeding fails, the new user is deleted (cascading to its rows) and the error is rethrown, so the next sign-in attempt starts from scratch and the user never exists without defaults. Seeding is idempotent, so retries are safe.
- **Session boundary.** `authMiddleware` takes a session resolver, rejects with `401` when there is no valid session and exposes only `userId` to handlers. Nothing else in the request can set it. `GET /api/me` and `PATCH /api/me/locale` use it.
- **Environment.** `parseEnv` validates `DATABASE_URL`, `BETTER_AUTH_SECRET` (at least 32 characters), `BETTER_AUTH_URL` and the Google client pair with Zod at startup. The error names the variables and never prints values. The composition root is `shared/compose.ts`.
- **Web.** A `useSession` hook wraps the Better Auth client. The landing button calls `signIn.social` for Google and returns to `/home`; the `/sign-in` placeholder is gone. `RequireAuth` sends signed-out visitors to `/`, and `/` sends signed-in visitors to `/home` without waiting for the session to load. After sign-in, the interface language follows `user.locale`; changing it in the menu persists through `/api/me/locale`.
- **Tests.** Integration tests sign sessions with the real Better Auth context against the CI Postgres container and never call Google. End-to-end tests stub `GET /api/auth/get-session` to simulate a signed-in user.
- **Bundling.** The serverless bundle is ESM and includes `pg`, which needs `require`, so the build adds a `createRequire` banner.

## Alternatives considered
- Seeding on every sign-in: simpler, but ADR 0025 notes it would recreate defaults the user renamed.
- Seeding in a transaction with user creation: Better Auth does not expose its user insert inside our transaction, so compensation by deletion is used.

## Consequences
- Google sign-in does not work on Vercel preview URLs: Google rejects wildcard redirect URIs, so only the production and localhost callbacks are registered.
- Previews and CI need the five variables (see below); CI end-to-end uses fake values for the four non-database ones.
- Every future endpoint mounts `authMiddleware` and reads `c.get("userId")`.

## Environment variables
| Variable | Where it comes from |
| --- | --- |
| `DATABASE_URL` | Neon connection string. In Vercel, the Neon integration sets it per environment and gives each preview its own branch (ADR 0018). |
| `BETTER_AUTH_SECRET` | Random value generated by the owner: `openssl rand -base64 32`. Use a different one per environment. |
| `BETTER_AUTH_URL` | The public origin of the deployment: `https://miplata-beta.vercel.app` in production, `http://localhost:5173` locally. |
| `GOOGLE_CLIENT_ID` | Google Cloud Console, project `miplata-515616`, client `miplata-web`. |
| `GOOGLE_CLIENT_SECRET` | The same client; held only by the owner. |
